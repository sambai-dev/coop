# Rookhold product and architecture research — 2026-08-29

This record explains the evidence used to choose Rookhold's post-v0.3 direction.
It is a point-in-time engineering assessment, not a certification or a claim
that the reviewed vendors are equivalent. Vendor performance and security
claims were treated as claims unless independently testable from this
repository.

## Decision

Rookhold should remain a narrow, self-hosted execution control plane for short,
stateless agent jobs. It should not compete with cloud IDEs on persistent
workspaces, package installation, browsers, PTYs, preview ports, or GPUs.

The durable job identity, effective-policy receipt, and hash-chained evidence
record are the product's strongest differentiation. The next releases should
make that evidence portable and signed while allowing operators to choose a
stronger per-job runtime boundary.

## What changed around Rookhold

The 2026 sandbox market has converged on several expectations:

- a separate sandbox, application kernel, or microVM for each mutually
  distrusting workload;
- explicit lifecycle APIs with durable handles and safe retries;
- deny-by-default egress controls and trusted-side credential injection;
- immutable images or templates plus content-addressed artifacts;
- per-job resource telemetry and OpenTelemetry correlation;
- agent-native protocols instead of framework-specific adapters.

Representative primary documentation:

- [E2B architecture](https://github.com/e2b-dev/infra/blob/main/docs/ARCHITECTURE.md)
  documents a Firecracker microVM per sandbox.
- [Modal Sandboxes](https://modal.com/docs/guide/sandboxes) use gVisor for the
  standard sandbox tier and expose an additional VM tier.
- [Cloudflare Sandbox](https://developers.cloudflare.com/sandbox/) combines
  isolated execution with files, processes, streaming, and controlled outbound
  traffic.
- [Vercel Sandbox](https://vercel.com/docs/sandbox) uses per-sandbox
  Firecracker microVMs and exposes snapshots and lifecycle APIs.
- [gVisor's security architecture](https://gvisor.dev/docs/architecture_guide/intro/)
  explains why an application kernel materially reduces direct host-kernel
  exposure compared with namespaces and syscall filtering alone.
- [Linux Landlock](https://www.kernel.org/doc/html/latest/userspace-api/landlock.html)
  is useful defense in depth but remains a shared-kernel control.

The research did not find a reviewed public claim equivalent to Rookhold's
executor-observed effective-policy receipt plus per-job event hash chain. That
is an inference from the public documentation reviewed, not proof that no
private or undocumented equivalent exists.

## Protocol baseline

The current stable Model Context Protocol revision is
[`2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28).
It replaced protocol sessions and the mandatory initialize handshake with a
stateless, self-describing request model and `server/discover`. Long-running
operations use the opt-in
[`io.modelcontextprotocol/tasks`](https://modelcontextprotocol.io/extensions/tasks/overview)
extension. Rookhold's durable job IDs and cancellation lifecycle map naturally to
that extension, while older MCP hosts still require the 2025 handshake era.

Other protocol choices are deliberately narrower:

- A2A 1.0 is for peer agents, not tool execution, so it does not belong in
  Rookhold's core service today.
- [CloudEvents 1.0.2](https://github.com/cloudevents/spec/tree/ce%40v1.0.2)
  is a useful additive export format, but does not replace Rookhold's ordered store,
  authorization, retries, or receipt chain.
- [OpenAPI 3.2.0](https://spec.openapis.org/oas/v3.2.0.html) can describe
  sequential streams with `itemSchema`, but generator support remains uneven;
  a 3.1-compatible contract remains necessary for current consumers.
- [W3C Trace Context](https://www.w3.org/TR/trace-context/) is the stable
  correlation baseline. Trace identifiers are operational correlation, not
  execution evidence.

## Evidence format

There is no mature generic standard for an "agent execution receipt." The
portable composition selected for Rookhold is:

1. a versioned Rookhold execution predicate;
2. an [in-toto Statement/v1](https://github.com/in-toto/attestation/tree/v1.2.0/spec/v1);
3. a [DSSE](https://github.com/secure-systems-lab/dsse/blob/v1.0.2/protocol.md)
   envelope signing the exact statement bytes;
4. an operator-pinned Ed25519 public key or external KMS/HSM signer.

A signature proves which key asserted the receipt bytes. It does not prove the
semantic truth of the assertion, deterministic re-execution, or remote
attestation. Future transparency anchoring may use the SCITT architecture, but
it is not required for local signature verification.

## Repository audit results

Two independent adversarial passes found no P0 issue. The release-blocking
findings were:

| Severity | Finding | Required change |
|---|---|---|
| P1 | One tenant can occupy all global queued-job leases before fair dispatch applies. | Acquire a per-tenant queued lease atomically with the global lease and expose distinct tenant/global rejection semantics. |
| P1 | Retained SQLite data is not byte-metered and age-only retention cannot catch the permitted ingest rate. | Enforce transactional tenant/global logical-byte quotas, a filesystem reserve watermark, and catch-up retention. |
| P2 | A non-loopback bind can still use the public development key and unisolated subprocess backend when the environment label is omitted. | Fail closed unless a separate conspicuous public-development acknowledgement is present. |
| P2 | Per-job memory limits are not backed by an aggregate host-memory reservation. | Add weighted global memory permits and deployment-level memory ceilings. |

The reviews did not validate a cross-tenant job read, result, replay, stream,
ticket, cancellation, receipt, rootfs, cgroup, or seccomp bypass in v0.3.

The developer-contract audit also found concrete v0.3 drift:

- successful live cancellation returns an empty body while the MCP adapter
  interprets an empty body as cancellation failure;
- the stdio MCP server blocks all other requests while one long tool call waits;
- the adapter implements only the 2025 MCP handshake era;
- MCP limit schemas disagree with server ceilings;
- a post-submit SDK timeout can lose the durable job ID;
- TypeScript WebSocket frame decoding can reorder asynchronous Blob decoding;
- SDK package metadata and CI contain stale version/build assumptions.

## Accepted v0.4 scope

The evidence-backed v0.4 scope is:

- fair tenant admission, aggregate memory budgeting, logical storage quotas,
  disk reserve checks, and safer public-bind validation;
- tenant-scoped durable submission idempotency;
- typed, idempotent cancellation and SDK reconnect/cursor correctness;
- dual-era MCP with the 2026 stateless protocol and opt-in Tasks;
- portable signed receipt envelopes and offline verification;
- request/trace correlation and bounded, low-cardinality operational metrics;
- an explicit isolation-class/runtime-provider contract.

A gVisor provider is release-eligible only after real per-job create, ready,
execute, cancel, timeout, wait, delete, crash-recovery, and hostile containment
gates pass. Merely running the whole Rookhold service inside gVisor is not per-job
tenant isolation.

## Deferred category expansion

The following remain deliberate future work rather than hidden promises:

- persistent workspaces, snapshots after tenant execution, PTYs, browsers, and
  inbound preview ports;
- arbitrary caller-selected OCI images;
- general network access instead of a destination-bound credential broker;
- multi-node scheduling before a durable queue, distributed quotas, network
  database, and external event bus exist;
- confidential-computing claims before measured boot, fresh attestation,
  independently appraised evidence, and guest-held receipt keys exist;
- A2A agent identity for a service that is not itself an autonomous agent.

## Release acceptance rule

No new capability is described as production-ready unless its exact deployment
path has a non-skipped CI gate and its runtime-observed facts are represented
truthfully in capabilities and terminal evidence. Configuration intent alone
is not evidence that a control became effective.

## Implementation outcome

The v0.4 implementation follows the accepted scope: fair admission and
storage/memory ceilings, durable idempotency, scoped credentials and JWTs,
dual-era MCP with Tasks, gVisor per-job OCI execution, W3C correlation and
bounded metrics, plus portable Ed25519 DSSE/in-toto attestations. Independent
runtime and identity reviews reported no remaining validated P0/P1/P2 after
their fixes; the integrated reliability races are covered by deterministic
concurrency and restart tests.

The deferred category expansion remains deferred. In particular, the new
signature is not described as hardware attestation, the gVisor class is not
described as a VM, the public-key endpoint is not a trust anchor, and the
single-node SQLite architecture is not described as horizontally scalable.
